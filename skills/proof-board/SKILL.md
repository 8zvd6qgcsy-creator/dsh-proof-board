# 审阅台：产出 → 摆上台面 → 批注 → 改

审阅台是 DSH 里的一墙卡片：工作区里的演示、文档、表格、图片、网页、PDF 按修改时间排在侧栏「审阅台」里。
用户在上面点「通过 / 待改 / 待定」、写一句批注；agent 通过工具读写同一份数据。

**核心约定：批注是用户的评审结论，不是 agent 的自我表扬。**
agent 可以写批注（自己复核发现的问题、用户口头说的意见），但不要替用户把东西标成「通过」。

## 什么时候用

| 场景 | 动作 |
| --- | --- |
| 用户说"审一下"、"看看这版"、"摆到台面上" | `proof_board_scan` 先看有什么，再逐项 `proof_board_note` |
| 一次会话交付了多份文件 | 交付完扫一遍，确认都在台上，缺的说明原因 |
| 用户说"把批注给你"、"按批注改" | `proof_board_handoff` 拿清单 → 读清单 → 逐项改 |
| 用户口头给了评审意见 | 立刻 `proof_board_note` 记下来，别指望记在脑子里的 |
| 改完一轮 | 重新 `proof_board_scan`，把改好的标 `ok`，没改好的留 `fix` |

## 三个工具

- `proof_board_scan` — 扫工作区，按 mtime 倒序返回 `rel`、`kind`、`bytes`、`mtime`、`verdict`、`note`。
  `withNotes: "open"` 只看待改 / 待定的，`kinds` 只看某几类。默认工作区就是当前会话目录；换工作区传 `dir`。
- `proof_board_note` — 给一项写批注。`verdict`：`ok` / `fix` / `todo` / `clear`（撤销）；`text`：一句话，写清"改哪里、改成什么"。
- `proof_board_handoff` — 把批注整理成 `审阅清单-<时间>.md` 写进工作区根目录，返回绝对路径。
  然后**读这个文件**，按里面的顺序动手。

## 批注怎么写

好的批注是**一个动作**：

- `fix` + "第 4 页标题和三张图的间距不一致，统一成一倍行距"
- `fix` + "第 7 页饼图配色和主题色不搭，换成 accent 蓝的四个梯度"
- `todo` + "第 9 页的数据来源还没确认，先空着"
- `ok` + "封面字体和字重对了"

不要写："这里不太好看看起来怪怪的"、"整体感觉可以再优化"。用户自己和后面接手的人看不懂。

一次只写一个问题。同一项有两个问题就写两条 `proof_board_note`（后面的覆盖前面的文字，所以把两条合并成一句再写）。

## 别做的事

- 不要为了让台上好看而改文件时间戳（`touch`）：台面按 mtime 排序，那是给用户看"最新的是什么"的信号。
- 不要自己写脚本扫目录、写 JSON 批注：工具在 Host 进程里跑，能读写 App 数据目录；模型的 shell 沙箱写不进去。
- 不要在没有批注的情况下"替用户生成评审结论"，扫完如实报告有哪几项就行。
- 不要在扫完之前就说"都改好了"。扫完、比对 `verdict`，再说话。

## 交接清单长什么样

`proof_board_handoff` 生成的 Markdown 按待改优先排序，每项给出：文件名、相对路径、类型和体积、结论、批注。
改完一轮把它重新生成一次，用户手里永远是最新的一份。
